## 代码检查确认的问题

1. `DesktopAudioService` 使用每个 cue 的短冷却和 `PlayOneShot`，缺少跨 cue 的并发上限。不同界面声音可以叠加，长音仍未结束时同 cue 也可重播。
2. `CatchAccepted` 同时可由 `AcceptLatestCatch` 成功回调与 `OnFishCatchSettled` 发出，音效只按 250ms 冷却；相同收获经过两个入口或重发可能重复庆祝。
3. 当前结算 DTO 没有稳定的 `catchId/resultId`；不能仅凭“物种＋尺寸＋时间窗口”可靠去重，否则会误吞连续真实鱼获。正式实现须沿现有钓鱼轮次透传稳定 ID，或扩展结算事件身份后双端一致消费。
4. 音效按 Unity 逻辑 `casting/waiting` 即时播放；WPF 表现经过 IPC、资源异步解码及坐下／收手衔接，冷加载时存在声音提前的架构风险。实际差值尚未在 Windows 测量。
5. 重连时只有阶段字符串去重；连接／鱼塘会话边界未重置音频基线。首次快照不能触发旧抛竿或旧入水。
6. WPF 菜单大部分共用 click；聊天 Enter 和鼠标按钮未走统一音效入口；入水和咬钩复用 splash。成功自动猫叫频率与手动摸猫共用 2.5 秒间隔。
7. **普通其他玩家自动动作目前已经不发声**，这不是本轮发现的现存多人广播缺陷；此次继续保持，并防止后续动画关键点接入时误扩展到其他角色。

审计入口：`DesktopAudioService.cs`、`DesktopAppBootstrap.cs`、`OwnFishingPresenter.cs`、`SocialPondSessionController.cs`、WPF `App.xaml.cs`／`MainWindow.xaml.cs`／`OverlayPetActor.cs`。

## 拟采用的听感与事件规则

| 场景 | 触发点 | 相对音效滑杆增益 | 去重与频率 |
| --- | --- | --- | --- |
| 普通按钮、开关、面板开合 | 有效操作完成入口 | 0.60–0.65 | UI 共用 90ms 间隔；同一动作只选一个 cue |
| 音量滑杆 | 用户拖动采样 | 0.45 | 至少 180ms；程序刷新滑杆不响 |
| 成功／失败 | 真实操作结果 | 0.65 | 按操作 ID 去重；普通导航不追加成功声 |
| 抛竿／入水 | 自己的动画关键点已开始／浮漂入水 | 0.80／0.65 | 每轮每标记一次；取消后移除未执行标记 |
| 咬钩 | 新的真实 bite 事件 | 0.90 | 稳定事件 ID 去重；和 splash 分开，不被入水冷却吞掉 |
| 收杆 | 自己的收杆动画开始 | 0.65 | 一次收杆只发一次；不随每帧循环 |
| 脱钩 | 真实失败结果 | 0.60 | 短落水尾音；主动停钓不冒充脱钩 |
| 打窝 | 真实 groundbaiting 中的撒饵入水标记 | 0.50 | 720ms 动作每三轮最多一次（2.16s）；结束立即取消 |
| 鱼获确认 | 入包／自动回鱼真实成功结果 | 0.80 | ACK＋结算同一 ID 只发一次；新鱼获不误去重 |
| 手动猫叫 | 点击自己的猫，非拖动／取消 | 0.65 | 至少 2.5s，三种变体不连续重复 |
| 自动猫叫 | 成功庆祝声结束之后 | 0.65 | 至少 12s，仍受全局猫叫间隔限制 |
| 其他玩家 | 任意自动阶段 | 0 | 不播放 |

- 并发预算：UI 最多 1 个、钓鱼最多 2 个、猫叫最多 1 个；音乐独立。
- 钓鱼优先级：咬钩／收获 > 脱钩 > 抛竿／入水／收杆 > 撒饵；满额时替换低优先级，不排队补播过时动作。
- 咬钩时音乐临时降至滑杆值的 50%，保持 0.7s；收获保持 1.2s，然后平滑恢复。原本静音时保持静音。
- 快照仅恢复状态；连接失效、换塘、离席、取消动作时清理对应会话或轮次标记。
- 新参数均为试听默认值，用户可确认或指出音色／响度／频率调整，再接正式代码。
