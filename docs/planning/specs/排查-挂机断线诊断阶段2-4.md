## 0. 文档目的

在 P0 修复（重连取消 60s 清场定时器）落地后，仍可能有挂机异常来自：

| 来源 | 典型表现 |
|------|----------|
| 移动端后台 / 弱网 | Socket 断开、重连失败或超过 60s |
| 客户端主动 `leave_pond` | 切页、返回地图、未登录跳转 |
| 服务端重启 / 其他 | 内存状态丢失、需用 metrics 排除 |

本文档定义 **阶段 2（后台/弱网矩阵）**、**阶段 3（排除 leave_pond）**、**阶段 4（Admin/SQLite 对照真实 player_id）** 的**产品需求、埋点规范、测试矩阵与现场排查 SOP**。

**交付物**：

1. 可复现、可记录的弱网/后台测试能力（客户端）
2. 可区分「断线踢人」vs「主动离塘」的埋点（客户端 + 服务端）
3. 按 `player_id` 重建事件时间线的 Admin/SQLite 工具与操作手册

## 1. 阶段 2 — 后台 / 弱网矩阵

### 1.1 目标

量化各平台在挂机场景下的 **WebSocket 存活率、重连成功率、钓位保留率**，为「断线」类投诉提供可比对数据，而非依赖用户口述。

### 1.2 现状缺口

| 项 | 现状 | 缺口 |
|----|------|------|
| Socket 生命周期 | `usePondSocket` 仅 `setConnected(false)` | 无 `reason`、无本地时间线 |
| 应用前后台 | 无 `AppState` / `visibilitychange` | 无法关联「切后台 → disconnect」 |
| 弱网 | 无测试钩子 | 无法系统化复现 |
| 服务端 | 已有 `disconnect` / `reconnect` metrics | 需与客户端时间戳对齐 |

### 1.3 产品需求

#### R2-1 客户端 Socket 生命周期日志（必须）

在 `mobile/lib/usePondSocket.ts`（或抽 `mobile/lib/socketLifecycleLog.ts`）输出**结构化本地日志**，前缀统一 `[pond-socket]`，字段：

| 事件 | 触发时机 | 必填字段 |
|------|----------|----------|
| `connect` | `socket.on('connect')` | `ts`, `playerId`, `pondId`, `socketId`（若有） |
| `disconnect` | `socket.on('disconnect')` | `ts`, `playerId`, `pondId`, `reason`（Socket.io 断开原因） |
| `connect_error` | `socket.on('connect_error')` | `ts`, `message` |
| `reconnect_attempt` | `socket.io` `reconnect_attempt`（若启用） | `ts`, `attempt` |
| `join_pond_ok` | `join_pond` ack `ok` | `ts`, `userId`, `spotId`（snapshot 后补） |
| `join_pond_fail` | ack 失败 | `ts`, `error` |

**存储**：开发/测试构建写入 `console`；可选 `__DEV__` 下保留内存环形缓冲（最近 200 条），供 Admin Debug 面板导出（P2）。

#### R2-2 应用前后台状态（必须）

| 平台 | API | 日志事件 |
|------|-----|----------|
| iOS / Android | `AppState`（`react-native`） | `[pond-app] foreground` / `background` + `ts` |
| Web | `document.visibilitychange` | `[pond-app] visible` / `hidden` + `ts` |

**行为（本阶段仅观测，不改业务）**：

- 记录 `background` → 下一次 `disconnect` 的时间差 Δt
- 记录 `foreground` → 下一次 `connect` / `join_pond_ok` 的时间差 Δt

#### R2-3 连接状态 UI 探针（建议）

鱼塘页（`mobile/app/pond/[id].tsx`）在 **Debug 构建或 Admin 模式** 显示一行小字：

```text
连接: 已连接 | 阶段: waiting | spot: calm-spot-3 | 最近断开: 12s前(io server disconnect)
```

便于测试员现场截图，不要求正式版常驻。

#### R2-4 弱网模拟说明（测试规程，非代码）

| 环境 | 工具 | 说明 |
|------|------|------|
| Web | Chrome DevTools → Network → Slow 3G / Offline | 标准弱网 |
| Android 模拟器 | Extended controls → Cellular → Network type | 可选 |
| 真机 | 系统飞行模式 10s / 65s | 覆盖 60s 内外 |

### 1.4 测试矩阵（必须执行并填表）

每个用例：**占座 → 开始钓鱼 → 执行场景 → 观察 5 分钟或至异常**，记录结果。

**平台维度**：Web (Chrome) · Android · iOS（有设备则测，无则标 N/A）

| ID | 场景 | 操作 | 记录字段 | 预期（P0 已修） |
|----|------|------|----------|-----------------|
| M1 | 前台挂机 | 保持鱼塘页前台 15min | `disconnect` 次数、`bite_hook` 次数 | 0 次 disconnect；咬钩按 `FISH_BITE_CHECK_MS` 发生 |
| M2 | 前台挂机 60min | 同上 60min | 同上 + 内存/卡顿 | 无异常离位 |
| M3 | 后台 30s | 切到其他 App 30s 后回鱼塘 | `background`→`disconnect` Δt、`foreground`→`reconnect` Δt、`spotId` | 多数平台会 disconnect；60s 内回前台应重连且保位 |
| M4 | 后台 2min | 同 M3，2min | 同上 | 若 disconnect>60s：预期 `disconnect_timeout`、钓位释放 |
| M5 | 后台 5min | 同 M3，5min | 同上 | 同 M4 |
| M6 | 锁屏 2min | 锁屏后解锁回鱼塘 | 同 M3 | 记录平台差异 |
| M7 | 断网 10s | 飞行模式 10s 恢复 | 服务端 `disconnect`→`reconnect` 间隔、`spotId` | 重连成功；**不应**有 `disconnect_timeout` |
| M8 | 断网 65s | 飞行模式 65s 恢复 | 同上 | 应有 `disconnect_timeout`；需重新占座 |
| M9 | 弱网 Slow 3G | DevTools 限速挂机 15min | disconnect 频率、重连次数 | 统计弱网下的断线率 |

**结果表模板**（QA 填写，可附在 issue / 飞书）：

```markdown
| ID | 平台 | 结果 | disconnect次数 | reconnect | spot保留 | 备注 |
|----|------|------|----------------|-----------|----------|------|
| M7 | Android | PASS/FAIL | 1 | 1 | Y/N | |
```

### 1.5 验收标准（阶段 2）

| # | 标准 |
|---|------|
| A2-1 | 三类平台至少各完成 M1、M3、M7、M8 并留有日志或截图 |
| A2-2 | 每条 `disconnect` 日志含 `reason`；每条 `background` 可关联到时间线 |
| A2-3 | M7 在 P0 修复环境下 **无** `disconnect_timeout`；M8 **有** |
| A2-4 | 输出《弱网/后台测试报告》1 份，结论标明：断线主因是网络/后台 vs 主动离塘 |

## 2. 阶段 3 — 排除 `leave_pond`

### 2.1 目标

当用户反馈「离开钓位」时，能明确回答：**是否为客户端主动 `leave_pond`**（切页、卸载组件），而非服务端超时踢人。

### 2.2 现状（v0.5.1 修订后）

| 项 | 现状 |
|----|------|
| 客户端离塘 | **仅**显式「返回地图」`navigation_back` 与 `auth_redirect` 会 `leave_pond` |
| 切页导航 | 社交 / 资料 / Debug 等路由切换 **不** `leave_pond`；页面卸载仅 `socket.disconnect()` |
| 服务端 | `leave_pond` 有结构化日志与 metric；`disconnect` 走 60s 宽限 + reconnect |

**会触发 `leave_pond` 的客户端路径（v0.5.1）**：

| 触发 | 路径 | 原因码 |
|------|------|--------|
| 返回地图 | `AppHeader onBack` · `handleLeaveToMap` | `navigation_back` |
| 鉴权跳转 | `useRequireAuth` 未登录离开 | `auth_redirect` |

**不再触发 `leave_pond` 的客户端路径（v0.5.1）**：

| 触发 | 说明 |
|------|------|
| 打开社交 | 仅 `router.push('/social')`，依赖 disconnect 宽限 |
| 编辑资料 | 仅 `router.push('/profile')` |
| 组件卸载 | cleanup 仅 `socket.disconnect()` |
| 背包 / 商店 / 图鉴 Modal | 同页 Modal，不卸载鱼塘页 |

`navigation_social` / `navigation_profile` / `unmount` 保留在类型与历史 metrics 中**只读**，新客户端不再写入。

### 2.3 产品需求

#### R3-1 扩展 `leave_pond` 载荷（必须）

**共享类型** `shared/types.ts`：

```typescript
// 原: leave_pond: (pondId: string) => void;
leave_pond: (payload: { pondId: string; reason: LeavePondReason }) => void;

type LeavePondReason =
  | 'unmount'
  | 'navigation_back'
  | 'navigation_social'
  | 'navigation_profile'
  | 'pond_change'
  | 'auth_redirect'
  | 'user_explicit';  // 预留：未来「离开鱼塘」按钮
```

**兼容**：服务端同时接受 `string`（旧客户端）与 `object`（新客户端），旧格式记 `reason: 'legacy_unknown'`。

#### R3-2 客户端在所有离塘路径传入 `reason`（必须）

| 文件 | 改动 |
|------|------|
| `mobile/lib/usePondSocket.ts` | cleanup **仅** `socket.disconnect()`；`leftPondRef` 仅显式 `leavePondWithReason` 置位 |
| `mobile/app/pond/[id].tsx` | **仅** `handleLeaveToMap` 调用 `leavePondWithReason('navigation_back')`；社交/资料跳转不 leave |

**注意**：若 navigation 与 unmount 会 **重复** `leave_pond`，服务端应幂等（第二次 `leavePond` 无 session 则忽略），客户端应避免双发（优先 navigation 显式 leave，unmount 时检测已离开）。

#### R3-3 服务端 `leave_pond` 埋点（必须）

`server/src/index.ts` · `leave_pond` 处理器：

1. **结构化日志** `[leave_pond]`：`playerId`, `userId`, `pondId`, `spotId`, `fishingPhase`, `reason`, `ts`
2. **`fishing_metrics` 新事件** `leave_pond`：`payload: { reason, spotId, fishingPhase }`
3. 若用户正在 `fishing`，已有 `fishing_stop` 逻辑处不重复；仅补充 leave 归因

扩展 `FishingMetricEvent` 联合类型：`leave_pond`。

#### R3-4 归因决策规则（排查用，写入 runbook）

```text
同一 player_id、相近时间窗口（±5s）：

1. 存在 leave_pond → 主动离塘（看 reason 是否 navigation_*）
2. 存在 disconnect + disconnect_timeout，无 leave_pond → 断线超时踢人
3. 存在 disconnect + reconnect，无 disconnect_timeout → 短暂断线已恢复
4. 存在 fishing_stop 无 leave_pond → 收竿但未离塘（spot 可能仍保留 seated）
5. 仅有 fishing_start 后长时间无事件 → 查服务端是否重启 / 连接是否存活（阶段 2 日志）
```

### 2.4 验收标准（阶段 3）

| # | 标准 |
|---|------|
| A3-1 | 点击「社交」后，**无** `leave_pond`；可有 `disconnect`；60s 内回塘 `joinKind=reconnect` |
| A3-2 | 直接关 Tab / 杀进程可能无 leave（预期），与 navigation 场景区分 |
| A3-3 | 挂机异常工单能用 SQL 排除「用户是否自己切走」 |
| A3-4 | `leave_pond` 与 `disconnect_timeout` 无重复计数同一次离塘（幂等） |

## 3. 阶段 4 — Admin / SQLite 对照真实 `player_id`

### 3.1 目标

给定投诉用户的 `player_id`（或昵称反查），在 **5 分钟内** 重建挂机时段的事件时间线，判断根因类别。

### 3.2 现状可用手段

| 手段 | 路径 | 局限 |
|------|------|------|
| 聚合 metrics | `GET /api/admin/metrics/fishing?hours=` | 无单用户时间线 |
| 鱼塘 Debug | `GET /api/admin/ponds/:pondId/fishing-debug?playerId=` | 仅当前快照，无历史 |
| 错误日志 | `GET /api/admin/logs` | 非结构化 disconnect 历史 |
| SQLite | `fishing_metrics` 表 | 需手写 SQL，无索引 `player_id` |

**P0 已入库事件**：`disconnect`, `reconnect`, `disconnect_timeout`（及既有 `fishing_start/stop`, `bite_hook`, `catch_accept`, `escape` 等）。

### 3.3 产品需求

#### R4-1 单用户事件时间线 API（必须）

```
GET /api/admin/metrics/fishing/player/:playerId?hours=24&limit=500
```

**响应**：

```typescript
{
  playerId: string;
  hours: number;
  events: Array<{
    id: string;
    eventType: string;
    pondId: string | null;
    payload: Record<string, unknown>;
    createdAt: number;  // ms
  }>;
  summary: {
    disconnectCount: number;
    reconnectCount: number;
    disconnectTimeoutCount: number;
    leavePondCount: number;
    fishingStartCount: number;
    biteHookCount: number;
    lastEventAt: number | null;
  };
}
```

实现：`server/src/fishingMetrics.ts` 新增 `getPlayerFishingTimeline(playerId, hours, limit)`；`admin.ts` 注册路由。

#### R4-2 SQLite 索引（必须）

```sql
CREATE INDEX IF NOT EXISTS idx_fishing_metrics_player_time
  ON fishing_metrics(player_id, created_at DESC);
```

写入 migration（如 `server/src/migrations/fishing_metrics_player_idx.ts`）。

#### R4-3 SQL 对照手册（文档 + 可复制脚本）

**按 player_id 查最近事件**：

```sql
SELECT datetime(created_at/1000, 'unixepoch', 'localtime') AS at,
       event_type, pond_id, payload
FROM fishing_metrics
WHERE player_id = :player_id
ORDER BY created_at DESC
LIMIT 100;
```

**查断线相关序列**：

```sql
SELECT datetime(created_at/1000, 'unixepoch', 'localtime') AS at,
       event_type, payload
FROM fishing_metrics
WHERE player_id = :player_id
  AND event_type IN ('disconnect', 'reconnect', 'disconnect_timeout', 'leave_pond', 'fishing_start', 'fishing_stop')
  AND created_at >= :since_ms
ORDER BY created_at ASC;
```

**昵称反查 player_id**：

```sql
SELECT player_id, nickname FROM players WHERE nickname LIKE '%' || :name || '%';
```

**今日钓鱼时长（验证是否仍在钓）**：

```sql
SELECT fishing_ms, date FROM daily_fishing
WHERE player_id = :player_id ORDER BY date DESC LIMIT 7;
```

#### R4-4 现场排查 SOP（必须写入 Admin 文档注释或本 spec）

**输入**：`player_id`、大概事发时间（本地时区）、`pond_id`（若知）

**步骤**：

| 步 | 动作 | 判定 |
|----|------|------|
| 1 | 调 `GET .../metrics/fishing/player/:id?hours=2` | 拉取时间线 |
| 2 | 定位事发窗口内最后一条 `fishing_start` | 确认挂机起点 |
| 3 | 之后是否有 `leave_pond` | **有** → 主动离塘（看 reason） |
| 4 | 之后是否有 `disconnect` | **无** → 非断线；查服务端重启 |
| 5 | `disconnect` 后是否有 `reconnect` | **有** → 短暂断线 |
| 6 | 是否有 `disconnect_timeout` | **有** → 超 60s 未回，钓位释放符合设计 |
| 7 | `reconnect` 后是否仍有 `disconnect_timeout` | **有** → P0 回归失败 |
| 8 | 同期 `bite_hook` 间隔 | 断线期间应无 bite；重连后恢复 |
| 9 | `GET .../fishing-debug?playerId=` 看当前是否在塘 | 仅作现状快照 |
| 10 | `GET /api/admin/logs` 查服务端异常 | OOM、未捕获错误 |

**输出模板**：

```markdown
## 挂机异常排查 — {nickname} ({player_id})
- 事发时间：...
- 结论：主动离塘 | 断线超时 | 短暂断线已恢复 | 服务端重启 | 待复现
- 证据：disconnect×N, reconnect×N, leave_pond(reason=...), ...
- 建议：...
```

#### R4-5 Admin UI：玩家时间线面板（建议）

在 `mobile/components/AdminMetricsPanel.tsx` 或 Admin 页增加：

- 输入框：`player_id`
- 按钮：「查询时间线」
- 表格：时间 / 事件 / pond / payload 摘要

调用 R4-1 API。无 UI 时可用 curl：

```bash
curl -s -H "X-Admin-Key: $ADMIN_KEY" \
  "http://localhost:3001/api/admin/metrics/fishing/player/PLAYER_ID?hours=24" | jq .
```

### 3.4 事件解读速查表

| 事件序列 | 含义 | 用户感知 |
|----------|------|----------|
| `fishing_start` → … → `leave_pond(navigation_back)` | 返回地图 | 主动离塘 |
| `fishing_start` → `disconnect` → `reconnect`（无 leave） | 切社交/Debug 后回塘 | 宽限内恢复，计时连续 |
| `disconnect` → `reconnect`（无 timeout） | 弱网恢复 | 可能短暂卡顿 |
| `disconnect` → `disconnect_timeout` | 超 60s | 被踢出鱼塘 |
| `disconnect` → `reconnect` → `disconnect_timeout` | **P0 Bug 回归** | 重连后仍被踢 |
| `fishing_start` 后 2h 无事件 | 连接可能仍存活或客户端未上报 | 对照阶段 2 日志 |
| `fishing_stop` 无 `leave_pond` | 收竿坐凳 | 仍在塘、占座 |

### 3.5 验收标准（阶段 4）

| # | 标准 |
|---|------|
| A4-1 | API 对测试 `player_id` 返回按时间排序的完整序列 |
| A4-2 | 用真实或模拟投诉案例走通 SOP，30 分钟内出结论 |
| A4-3 | SQL 手册在 SQLite 客户端可执行，索引生效（`EXPLAIN QUERY PLAN` 走索引） |
| A4-4 | `summary` 计数与 `events` 一致 |
