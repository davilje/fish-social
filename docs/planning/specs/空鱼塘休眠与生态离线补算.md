## 1. 背景与目标

当前服务端 `tickAllPonds()` 会按固定周期遍历所有鱼塘。随着 Steam 桌面端和挂机鱼塘增加，即使没有玩家的鱼塘也会持续执行生态 Tick。

本需求将鱼塘分为两种运行状态：

```text
活跃鱼塘：
  有连接玩家 → 高频实时 Tick → 广播生态变化

空鱼塘：
  无连接玩家 → 停止高频 Tick → 记录最后模拟时间
  下次进入 → 按离线时间补算 → 恢复实时 Tick
```

目标是降低无效计算，同时保证空鱼塘中的鱼群迁移、成长、数量变化和钓点状态不会因为无人在线而停止。

---

## 2. 已确认规则

- 空鱼塘不运行高频生态 Tick。
- 空鱼塘的鱼群成长、迁移和数量补充仍然生效。
- 玩家重新进入鱼塘时，服务端根据持久化时间差补算。
- 补算必须在数据库事务中完成，并且重复唤醒不能重复结算。
- 鱼的成长以出生时间和成长公式为基础，不能因为补算次数重复叠加。
- 迁移和补充不能因为服务器重启、重复进塘或并发唤醒重复执行。
- 活跃鱼塘继续使用现有实时生态逻辑。
- 空鱼塘不需要一塘一个服务器进程。
- 鱼塘状态继续由 Node 服务端和数据库权威保存。

---

## 3. 术语和状态

### 3.1 鱼塘活跃状态

建议以“鱼塘是否存在连接玩家”作为是否运行实时生态 Tick 的第一判断：

```text
roomUserCount > 0 → active
roomUserCount = 0 → sleeping
```

玩家连接但无人钓鱼时，鱼塘仍可视为活跃，以保证玩家看到的生态变化和社交状态一致。

### 3.2 持久化时间字段

在 `pond_state` 中新增：

```text
last_simulated_at INTEGER NOT NULL
```

字段含义：

- 表示鱼塘生态状态最后一次被推进到的时间。
- 不能在只读取快照时前移。
- 只有实时 Tick 成功完成，或离线补算事务成功提交后才能前移。

现有字段继续保留并明确语义：

- `last_weight_refresh`：钓点咬钩权重刷新时间。
- `last_supplement_at`：鱼群补充时间。
- `last_migration_at`：鱼群迁移时间。

## 4. 离线补算范围

### 4.1 鱼成长

成长优先使用现有 `growFishSizeV2` 的绝对时间曲线：

```text
size = growth(birthSize, bornAt, now)
```

要求：

- 不按离线 Tick 次数重复累加。
- 同一条鱼多次补算得到相同结果。
- 成长结果不能超过现有物种和品质上限。

### 4.2 鱼群迁移

迁移按现有 `FISH_MIGRATION_CHECK_MS` 和 `FISH_MIGRATION_FRACTION` 规则推进。

要求：

- 根据 `last_migration_at` 计算应发生的迁移事件。
- 每个迁移事件最多处理一次。
- 迁移目的地继续使用栖息地权重和钓点列表。
- 离线补算必须使用可重复的事件种子或等价幂等标记，不能因为重试随机改变并重复迁移。
- 鱼塘恢复后，下一次实时 Tick 从新的 `last_migration_at` 继续。

建议事件种子：

```text
seed = hash(pondId + migrationEventAt + fishId)
```

不得使用无法记录事件边界的纯 `Math.random()` 作为离线补算唯一依据。

### 4.3 鱼群补充

补充继续遵循当前池塘配置和最大数量：

- 不超过 `maxPopulation`。
- 按离线期间应发生的补充检查推进。
- 离线补算时不依赖当前在线钓鱼人数。
- 补充结果达到上限后停止新增。
- 不能因重复唤醒重复添加同一批鱼。

### 4.4 钓点权重

- 离线期间不需要逐次重放每次权重随机刷新。
- 唤醒时若权重已过期，事务内刷新一次。
- 刷新后更新 `last_weight_refresh`。
- 快照使用唤醒后的最新权重。

## 5. 补算接口与事务

建议新增内部接口：

```text
ensurePondEcologyCurrent(pondId, now?)
wakePondEcology(pondId, now?)
sleepPondEcology(pondId, now?)
```

建议流程：

```text
join_pond / 读取鱼塘前
  → 获取 pond_state
  → 判断 last_simulated_at 与 now 的差值
  → 事务内补算成长/迁移/补充/权重
  → 更新 last_* 字段
  → 提交事务
  → 生成 pond_snapshot
  → 恢复该鱼塘实时 Tick
```

事务要求：

- 同一个鱼塘同一时刻只能有一个补算事务。
- 补算所有写入和 `last_simulated_at` 更新必须同事务提交。
- 事务失败时不得前移时间锚点。
- 重试必须安全。
- 服务器重启后可从 `pond_state` 继续。

---

## 6. 实时 Tick 改造

当前 `tickAllPonds()` 不应无条件遍历所有鱼塘。

建议改为：

```text
for pond in ponds:
  if roomUserCount(pond) == 0:
    continue
  tickPondEcology(pond)
  emit pond_ecology_updated
```

注意：

- 进入鱼塘时先执行唤醒补算。
- 离开最后一个玩家后不再广播生态 Tick。
- 玩家再次进入时先补算，再发送 `pond_snapshot`。
- 不得在空鱼塘期间继续通过 Socket 广播无接收者的数据。

---

## 7. 大时间跨度和性能保护

需要配置补算保护，避免玩家离线数月导致一次请求执行海量事件：

```text
POND_OFFLINE_MAX_REPLAY_STEPS
POND_OFFLINE_MAX_CATCHUP_MS
```

建议策略：

- 成长使用绝对时间公式，直接计算。
- 迁移和补充按事件步数上限分段处理。
- 超过上限时使用确定性的压缩补算策略，并明确记录 `catchupCompacted`。
- 不允许静默跳过离线时长。
- 记录补算耗时、离线时长、迁移数量、补充数量和是否压缩。

## 8. 验收场景

### 基础休眠

- [x] 无人鱼塘不执行高频生态 Tick。
- [x] 无人鱼塘不广播 `pond_ecology_updated`。
- [x] 鱼塘状态保留在数据库。

### 成长

- [x] 空塘等待一段模拟时间后重新进入，鱼体长按时间变化。
- [x] 重复读取快照不会重复增加体长。
- [x] 服务器重启后成长结果连续。

### 迁移与补充

- [x] 离线期间鱼群发生迁移。
- [x] 离线期间鱼群可按规则补充，但不超过上限。
- [x] 同一离线时间段重复唤醒不会重复迁移或补充。
- [x] 迁移和补充跨事务失败重试仍然幂等。

### 活跃恢复

- [x] 玩家进入时先完成补算，再收到快照。
- [x] 玩家进入后恢复实时生态 Tick。
- [x] 多人同时进入不会重复执行唤醒补算。
- [x] 最后一名玩家离开后鱼塘进入休眠。

### 性能和安全

- [x] 20 个空鱼塘不会持续执行完整生态循环。
- [x] 大时间跨度补算有上限和压缩日志。
- [x] 补算失败不会前移时间锚点。
- [x] `last_simulated_at`、迁移和补充写入具有事务一致性。

## 10. 非目标

- 不改变鱼群物种、品质和成长曲线的产品数值。

- 不实现 Steam 登录、Lobby 或 Relay。
- 不在客户端做生态权威计算。
- 不要求空鱼塘每秒模拟玩家可见动画。
