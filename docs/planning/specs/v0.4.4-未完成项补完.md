## 0. 文档目的

`v0.4.4` 主体能力已落地，但还遗留 3 个关键缺口：

1. `phase_transition_invalid`（P1）尚未实现
2. P2 性能类埋点尚未实现（tick 耗时、broadcast fanout、slow query、admin route duration）
3. `pending_catch_expired` 仅有事件逻辑，缺少“真实超时场景”慢测 verify

本补丁文档用于后端一次性补齐上述缺口，并形成可回归验证的最小闭环。

## 2. 风险

### 2.1 `phase_transition_invalid` 缺失风险（P1）

当前仅记录“发生了 phase 迁移”，但不检测“迁移是否合法”，导致：

1. 非法跳转（如 `idle -> hooked`）可能静默发生
2. 恢复路径 bug 只能通过用户反馈发现
3. timeline 能看到跳转，但无法自动标红异常

### 2.2 P2 性能埋点缺失风险（P2）

缺少性能信号会导致：

1. tick 堵塞无法提前发现
2. 广播扇出放大无可见性
3. SQLite 慢查询定位困难
4. Admin 接口卡顿无证据链

### 2.3 pending 超时慢测缺失风险（P1）

`pending_catch_expired` 虽已写入逻辑，但未经过真实时间流逝验证：

1. 可能因 timer 生命周期问题误报/漏报
2. 回归测试无法覆盖“超时触发路径”

## 3. 补完需求

## 3.1 `phase_transition_invalid` 检测与日志（P1，必须）

### R1 规则定义

新增合法迁移白名单（含 reconnect 特例），非法则上报：

| from | 允许 to |
|------|---------|
| `idle` | `seated`, `disconnected` |
| `seated` | `baiting`, `idle`, `disconnected` |
| `baiting` | `casting`, `seated`, `disconnected` |
| `casting` | `waiting`, `disconnected` |
| `waiting` | `hooked`, `stopping`, `disconnected` |
| `hooked` | `resolving`, `waiting`, `disconnected` |
| `resolving` | `baiting`, `seated`, `idle`, `disconnected` |
| `stopping` | `seated`, `idle`, `disconnected` |
| `disconnected` | `waiting`, `seated`, `idle`, `hooked`, `resolving` |

说明：

1. 允许 `hooked -> waiting`（hook context 丢失兜底）
2. 允许 `disconnected -> hooked/resolving`（重连续接）
3. 白名单需集中维护，避免散落在 switch 中

### R2 检测点

在统一 `transitionPhase(...)` 前或后执行校验：

1. 若非法，记录结构化日志 `[phase_transition_invalid]`
2. 追加 `recordFishingMetric('phase_transition_invalid', ...)`
3. 不阻塞主流程（先观测，后治理）

### R3 字段

必填字段：

- `playerId`, `userId`, `socketId`
- `pondId`, `spotId`
- `fromPhase`, `toPhase`, `cause`
- `phaseElapsedMs`
- `ts`

可选字段：

- `phaseDeadlineTs`
- `isReconnectPath`

### R4 验收

1. 人工构造一条非法迁移能看到日志与 metrics
2. 正常路径不误报
3. timeline summary 可统计 `phaseTransitionInvalidCount`

## 3.2 P2 性能埋点（P2，必须）

### R5 tick 耗时埋点

在 `index.ts` 的周期任务中增加耗时统计（结构化日志）：

| 任务 | 事件名 | 字段 |
|------|--------|------|
| `tickFishingPhases` | `tick_fishing_phases_duration_ms` | `durationMs`, `pondCount`, `activeUsers` |
| `processWaitingBiteTick` 外层循环 | `bite_check_loop_duration_ms` | `durationMs`, `candidates`, `triggered` |
| `tickAllPonds` 生态任务 | `ecology_tick_duration_ms` | `durationMs`, `pondCount` |

### R6 broadcast fanout 埋点

对主要广播点记录 fanout：

| 广播 | 事件名 | 字段 |
|------|--------|------|
| `pond_user_updated`（每秒循环） | `socket_broadcast_fanout` | `channel`, `pondId`, `fanoutCount` |
| `pond_ecology_updated` | `socket_broadcast_fanout` | 同上 |
| 关键状态广播（join/leave） | `socket_broadcast_fanout` | 同上 |

说明：`fanoutCount` 可用 `io.sockets.adapter.rooms.get(pondId)?.size ?? 0`。

### R7 slow query 埋点

在 DB 调用层新增耗时包装（最小侵入）：

1. 给高频/关键查询包一层 `timedQuery(name, fn)`
2. 超过阈值（默认 `SLOW_QUERY_MS=30`）打 `[slow_query]`
3. 字段：`queryName`, `durationMs`, `thresholdMs`, `rows?`, `ts`

### R8 admin route duration 埋点

在 `admin.ts` 加中间件（或每路由包裹）：

1. 记录 `admin_route_duration_ms`
2. 字段：`path`, `method`, `status`, `durationMs`, `ts`
3. 超阈值（建议 200ms）额外记 `admin_route_slow`

### R9 验收

1. 启服后每类性能事件都能在日志中看到至少 1 条
2. 人为触发慢查询或加 sleep，能命中 `slow_query`
3. 调 Admin API 能产生日志并含状态码和耗时

## 3.3 `pending_catch_expired` 真实超时慢测 verify（P1，必须）

### R10 新增慢测脚本/用例

在现有 verify 基础上新增一个慢测 case（建议脚本：`scripts/verify-pending-timeout.ts` 或扩展现有）：

步骤：

1. 创建测试玩家并进入钓鱼态
2. 通过真实 `lockPendingCatch(...)` 生成 pending
3. 不调用 `acceptCatch`
4. 等待 `PENDING_CATCH_TIMEOUT_MS + buffer`（建议 +1500ms）
5. 查询 timeline/metrics，断言出现 `pending_catch_expired`

### R11 运行方式

建议 npm script：

```json
"verify:pending-timeout": "npm run build:shared && npx tsx scripts/verify-pending-timeout.ts --slow"
```

同时支持：

- 默认快速模式（skip 慢测，打印提示）
- `--slow` 才真正等待超时

### R12 验收

1. `--slow` 跑完后断言 `pending_catch_expired >= 1`
2. pending 锁应释放（同 fish 可再次被锁）
3. 快速模式不会阻塞 CI
