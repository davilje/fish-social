## 1. 背景

`fishing_phase_transition` 在停写 tick 后仍是高频、**payload 最肥**（常含 fromPhase/toPhase 全文 + cause + deadline 等）。  
优化目标：**库内只存短码**，语义仍可还原；**必须保留 from→to**（非法跳转与排障需要），**不能**压成「只有当前阶段 1～4」。

完整阶段共 **9** 个，编号 **0～8**（不是 1～4）。

---

## 2. 相位编号字典（权威）

| 码 | `FishingPhase` |
|----|----------------|
| 0 | `idle` |
| 1 | `seated` |
| 2 | `baiting` |
| 3 | `casting` |
| 4 | `waiting` |
| 5 | `hooked` |
| 6 | `resolving` |
| 7 | `stopping` |
| 8 | `disconnected` |

- 字典放在 `shared/`（如 `phaseCodes.ts`），服务端与埋点表共同引用说明。  
- `from` 首次进入可为 `null` / 省略；落库可用 `-1` 或不写 `f` 字段（实现二选一，schema 写清）。

---

## 3. 落库契约（P0）

### 3.1 `fishing_phase_transition` metrics payload（默认）

**只允许**短字段（示例）：

```json
{ "f": 4, "t": 5, "c": "bite_hook" }
```

| 键 | 含义 |
|----|------|
| `f` | from 相位码 0～8；起点可缺省或 `-1` |
| `t` | to 相位码 0～8（必填） |
| `c` | cause 短码（沿用现有 cause 字符串的缩写表，或保留原 cause 若已短） |

**禁止**默认写入：`phaseDeadlineTs`、大段 reason 文案、整份 user 快照、重复的 `fishingPhase` 长字符串等。

### 3.2 日志（stdout / pino）

结构化日志**仍可用全称** `fromPhase`/`toPhase`，便于人读；与 metrics 瘦身不冲突。

### 3.3 `phase_transition_invalid`

同样改为短码 `f`/`t`/`c`（或并行保留可读字段仅打日志）。metrics/日志至少一端能还原 from→to。

---

## 4. 可选 P1（同需求可分期）

| 项 | 说明 |
|----|------|
| `METRICS_SKIP_BOTS=1` | 生产/主库跳过 `playerId` 以 `bot-` 开头的 metrics 写入（压测旁路库除外） |
| 相位采样 | 合法跳转按 N% 落库；**非法跳转始终落库** |
| 清理历史 | 一次性 DELETE 旧胖 payload 的 transition 行（或整表 archive 后重来） |

---

## 5. 埋点表与 schema 同步（强制）

实现本需求时必须：

1. 更新 `shared/metrics-schema.ts`  
2. 更新 `scripts/build-metrics-events-xlsx.py` 中 `fishing_phase_transition` / `phase_transition_invalid` 行  
3. 运行 `npm run planning:metrics-xlsx` 重生根目录 `v0.4.4-埋点表清单.xlsx`（及 reports 副本）  

后续凡改埋点，遵守项目 Skill **metrics-catalog-sync**（见 `.cursor/skills/metrics-catalog-sync/SKILL.md`）。
