## 0. 文档目的

当前 `fish-social` 服务端已具备：

1. `Express` HTTP API
2. `Socket.io` 实时鱼塘会话
3. `SQLite` 持久化玩家/生态/配置/metrics
4. 基于内存的鱼塘用户、断线恢复、钓鱼状态机

这套架构适合单机开发与小规模联调，但在“挂机、断线、重连、鱼塘广播、线上排查”场景下，已经暴露出明显的**可恢复性、可扩展性、可观测性**短板。

本文档给出：

1. **现状**：当前服务端真实架构与职责分层
2. **风险**：按 P0/P1/P2 归类的架构缺陷
3. **埋点事件表**：建议新增或补全的服务端事件
4. **字段定义**：统一埋点 payload 规范
5. **优先级与实施顺序**：便于后端分批实现

## 1. 现状

### 1.1 当前服务端架构

| 层 | 主要文件 | 作用 |
|----|----------|------|
| 入口层 | `server/src/index.ts` | HTTP + Socket.io 启动、事件注册、全局 tick、广播 |
| 会话层 | `server/src/gameState.ts` | `sessions`、`pondUsers`、`pondChats`、钓位占用、join/leave |
| 状态机层 | `server/src/fishingStateMachine.ts` | phase 转移、disconnect 宽限、hook/reconnect 续接 |
| 咬钩/领取层 | `server/src/fishingSession.ts`、`server/src/inventory.ts` | 咬钩判定、pending catch、领取结果 |
| 生态层 | `server/src/pondEcology.ts` | 鱼塘生态、迁徙、补充、生长 |
| 管理层 | `server/src/admin.ts` | debug、metrics、timeline、config、日志 |
| 持久化层 | `server/src/db.ts` + migrations | SQLite 表结构与迁移 |

### 1.2 状态存储现状

| 数据 | 存储位置 | 备注 |
|------|----------|------|
| 玩家在线鱼塘状态 | **内存** | `pondUsers` |
| socket 会话 | **内存** | `sessions`、`socketByUserId`、`playerSockets` |
| phase / 钓位 / 断线恢复中间态 | **内存** | `fishingPhase`、`spotId`、`disconnectTimers`、`hookContextByUser` |
| 玩家资料 / 背包 / 每日时长 | SQLite | 已持久化 |
| 生态鱼群 | SQLite | 已持久化 |
| metrics | SQLite | 已持久化 |

### 1.3 当前运行模型

| 机制 | 实现 |
|------|------|
| phase 推进 | `setInterval(..., 200)` |
| 会话时长广播 | `setInterval(..., 1000)` |
| 咬钩检测 | `scheduleRuntimeInterval(..., getBiteCheckMs)` |
| 生态 tick | `setInterval(..., POND_ECOSYSTEM_TICK_MS)` |
| disconnect 清场 | per-user `setTimeout(60_000)` |

**结论**：当前是典型的“**单进程权威服 + 内存实时态 + SQLite 持久化补充**”。

## 2. 风险

### 2.1 P0 风险（会直接影响挂机/在线一致性）

#### RISK-P0-1 实时核心状态过度依赖内存

| 现状 | 风险 | 影响 |
|------|------|------|
| `spotId`、`fishingPhase`、`disconnectTimers`、`hookContextByUser` 在内存 | 服务重启后全部丢失 | 玩家离塘、钓位丢失、phase 无法恢复 |

**说明**：虽然生态已落库，但“玩家在线态”仍不持久化，无法满足严格意义上的热恢复。

#### RISK-P0-2 定时器与状态推进分散

| 现状 | 风险 | 影响 |
|------|------|------|
| 同时存在全局 tick 与 per-user `setTimeout` | 时序难推理，容易出现恢复漏取消、重复推进 | 重连误踢、状态漂移、隐蔽边界 bug |

**例子**：之前已修过的“reconnect 后未取消 disconnect timer”就是该类风险的直接体现。

#### RISK-P0-3 会话主键多套并存

| 主键 | 用途 |
|------|------|
| `socketId` | 当前连接 |
| `userId` | 鱼塘内临时用户 |
| `playerId` | 玩家长期身份 |

**风险**：日志、广播、重连、社交、Admin 查询若不统一主键，会导致排查困难和映射残留。

---

### 2.2 P1 风险（会影响排查效率和中期演进）

#### RISK-P1-1 `index.ts` 入口层职责过重

当前 `index.ts` 同时负责：

1. socket 事件注册
2. HTTP 组装
3. 广播
4. 定时 tick
5. reconnect 流程
6. 启停控制

**风险**：难测试、难拆分、改动面大、容易引入回归。

#### RISK-P1-2 phase 迁移缺少统一埋点

虽然已有结果型 metrics：

- `fishing_start`
- `fishing_stop`
- `bite_hook`
- `catch_accept`
- `escape`
- `disconnect`
- `reconnect`

但仍缺少最关键的：

- `fromPhase -> toPhase`
- `cause`
- `耗时`

这使得很多问题只能靠猜，而无法靠 timeline 还原。

#### RISK-P1-3 客户端可见异常与服务端历史事件仍未完全闭环

例如：

- “挂着没鱼”
- “角色突然跑到底部”
- “重连后没提示”

如果没有完整 phase/event chain，很难快速回答：

1. 是断线？
2. 是 leave？
3. 是超时？
4. 是 bait 不足？
5. 是 pending catch 超时？

---

### 2.3 P2 风险（偏扩展性/容量）

#### RISK-P2-1 不能水平扩容

内存态绑定单实例，当前无法安全多开 server 实例。

#### RISK-P2-2 缺少性能与容量指标

缺少：

- tick 耗时
- 广播扇出量
- snapshot 构建耗时
- SQLite 查询耗时
- event loop lag

未来在线人数一上来，可能先出现卡顿和广播延迟，而不是功能 bug。

#### RISK-P2-3 Admin 更像 debug 工具，不是完整 observability 平台

当前 Admin 能看摘要和时间线，但仍缺：

- phase 热力统计
- reconnect 成功率
- disconnect reason 分布
- 每塘负载趋势

## 3. 埋点设计原则

### 3.1 原则

1. **统一主键**：以 `playerId` 为主，`userId/socketId` 为辅助
2. **事件可串联**：每个事件尽量带 `pondId`、`spotId`、`fishingPhase`
3. **可解释原因**：状态变化必须带 `cause`
4. **区分业务 vs 性能**：业务事件进 `fishing_metrics`，性能事件先走结构化日志，后续再评估是否入库
5. **避免高频爆表**：高频 tick 事件默认聚合，不逐条入库

### 3.2 埋点层级

| 层级 | 类型 | 建议落点 |
|------|------|----------|
| L1 | 业务关键事件 | SQLite `fishing_metrics` |
| L2 | 高价值结构化日志 | `console.log(JSON)`，后续可接日志平台 |
| L3 | 高频性能指标 | 聚合日志 / Admin summary，不逐条写库 |

## 4. 埋点事件表

### 4.1 A 类：连接与会话事件（P0，必须）

| 事件名 | 类型 | 触发时机 | 当前状态 | 优先级 |
|--------|------|----------|----------|--------|
| `socket_connect` | 日志 | socket 建连成功 | 缺失 | P0 |
| `socket_disconnect` | metrics + 日志 | socket 断开 | 已有 `disconnect`，建议改名统一或保留别名 | P0 |
| `socket_connect_error` | 日志 | socket 建连失败 | 缺失 | P0 |
| `join_pond_attempt` | 日志 | 收到 `join_pond` | 缺失 | P0 |
| `join_pond_success` | metrics + 日志 | 新 join 或 reconnect join 成功 | 缺失 | P0 |
| `join_pond_fail` | metrics + 日志 | join 失败 | 缺失 | P0 |
| `leave_pond` | metrics + 日志 | 客户端主动离塘 | **已实现** | P0 |
| `disconnect_timeout` | metrics + 日志 | 60s 未重连清场 | **已实现** | P0 |
| `session_rebound` | 日志 | `playerId` 绑定到新 `socketId` | 缺失 | P1 |

### 4.2 B 类：钓位与鱼塘事件（P1，建议）

| 事件名 | 类型 | 触发时机 | 优先级 |
|--------|------|----------|--------|
| `spot_take_success` | metrics | 玩家成功占座 / 开始使用钓位 | P1 |
| `spot_take_fail` | metrics | 钓位被占、鱼塘满、无空位 | P1 |
| `spot_release` | metrics | 离塘、超时清场、离席释放 | P1 |
| `pond_full_reject` | metrics | `joinPond` 因人数满失败 | P1 |
| `bot_evicted_for_human` | metrics | 为真人腾位踢 bot | P1 |

### 4.3 C 类：状态机迁移事件（P0，必须）

**新增统一事件**：`fishing_phase_transition`

| from | to | cause 示例 |
|------|----|-------------|
| `idle` | `seated` | `take_spot` |
| `seated` | `baiting` | `start_fishing` |
| `baiting` | `casting` | `phase_timer_elapsed` |
| `casting` | `waiting` | `phase_timer_elapsed` |
| `waiting` | `hooked` | `bite_hook` |
| `hooked` | `resolving` | `hook_timeout` / `stop_fishing_escape` |
| `resolving` | `baiting` | `auto_continue` |
| `resolving` | `seated` | `bait_insufficient` / `stop_to_seated` |
| `*` | `disconnected` | `socket_disconnect` |
| `disconnected` | `waiting/seated/idle/hooked/resolving` | `socket_reconnect` |

| 事件名 | 类型 | 触发时机 | 优先级 |
|--------|------|----------|--------|
| `fishing_phase_transition` | metrics + 日志 | 每次 phase 改变 | P0 |
| `phase_transition_invalid` | 日志 | 检测到不应出现的 phase 跳转 | P1 |

### 4.4 D 类：咬钩与产出事件（P1，建议）

| 事件名 | 类型 | 触发时机 | 当前状态 | 优先级 |
|--------|------|----------|----------|--------|
| `bite_tick_miss` | metrics | waiting tick 未咬钩 | 缺失 | P1 |
| `bite_tick_hit` | metrics | waiting tick 咬钩成功 | 现有 `bite_hook` 可保留并补字段 | P1 |
| `pending_catch_created` | metrics | 进入待领取 | 缺失 | P1 |
| `pending_catch_accept` | metrics | 玩家领取 | 现有 `catch_accept` | P1 |
| `pending_catch_expired` | metrics | 待领取超时 | 缺失 | P1 |
| `bait_depleted` | metrics | 装饵时发现旧饵耗尽并切换 / 无饵 | 缺失 | P1 |
| `escape` | metrics | 脱钩 | 已有 | P1 |

### 4.5 E 类：系统性能事件（P2，建议）

| 事件名 | 类型 | 触发时机 | 优先级 |
|--------|------|----------|--------|
| `tick_fishing_phases_duration_ms` | 聚合日志 | 每轮 200ms tick 后记录耗时 | P2 |
| `bite_check_loop_duration_ms` | 聚合日志 | 每轮 bite 检测后记录耗时 | P2 |
| `snapshot_build_duration_ms` | 聚合日志 | `buildSnapshot` 完成后 | P2 |
| `socket_broadcast_fanout` | 聚合日志 | 广播前统计接收人数 | P2 |
| `sqlite_query_slow` | 日志 | 超阈值查询 | P2 |
| `admin_route_duration_ms` | 日志 | Admin 接口耗时 | P2 |

## 5. 字段定义

### 5.1 通用字段（所有业务事件）

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `ts` | number | 是 | `Date.now()` 毫秒时间戳 |
| `eventType` | string | 是 | 事件名 |
| `playerId` | string | 否 | 长期玩家身份；bot 可为空或 `bot-*` |
| `userId` | string | 否 | 鱼塘内临时用户 ID |
| `socketId` | string | 否 | 当前连接 ID |
| `pondId` | string | 否 | 鱼塘 ID |
| `spotId` | string \| null | 否 | 钓位 ID |
| `fishingPhase` | string \| null | 否 | 当前 phase |
| `isBot` | boolean | 否 | 是否机器人 |

### 5.2 连接类扩展字段

| 字段 | 类型 | 说明 |
|------|------|------|
| `reason` | string | disconnect / leave / fail 原因 |
| `disconnectDurationMs` | number | reconnect 时与上次 disconnect 间隔 |
| `joinKind` | `'fresh' \| 'reconnect'` | join 类型 |
| `ackError` | string | join 失败原因 |

### 5.3 phase 迁移字段

| 字段 | 类型 | 说明 |
|------|------|------|
| `fromPhase` | string \| null | 原 phase |
| `toPhase` | string | 新 phase |
| `cause` | string | 迁移原因 |
| `phaseElapsedMs` | number | 原 phase 已持续时长 |
| `phaseDeadlineTs` | number \| null | 新 phase 截止时间 |

**`cause` 建议枚举**：

- `take_spot`
- `start_fishing`
- `phase_timer_elapsed`
- `bite_hook`
- `hook_timeout`
- `stop_fishing`
- `stop_fishing_escape`
- `socket_disconnect`
- `socket_reconnect`
- `bait_insufficient`
- `auto_continue`
- `leave_pond`
- `disconnect_timeout`

### 5.4 咬钩与产出字段

| 字段 | 类型 | 说明 |
|------|------|------|
| `speciesId` | string | 鱼种 |
| `quality` | string | 品质 |
| `sizeM` | number | 尺寸 |
| `baitId` | string | 饵 |
| `tackleId` | string | 竿/渔具 |
| `pBite` | number | 本次 tick 咬钩概率 |
| `escapeRate` | number | 脱钩率 |
| `pendingCatchAgeMs` | number | 待领取持续时间 |

### 5.5 性能字段

| 字段 | 类型 | 说明 |
|------|------|------|
| `durationMs` | number | 执行耗时 |
| `userCount` | number | 鱼塘人数 |
| `activeFishingUsers` | number | 当前钓鱼人数 |
| `fanoutCount` | number | 广播接收人数 |
| `rows` | number | SQL 结果行数 |
| `thresholdMs` | number | 慢查询阈值 |

## 6. 优先级与实施顺序

### 6.1 第一批（P0，建议先做）

目标：先把“挂机 / 断线 / 重连 / 状态机”这条最常见排查链闭环。

| 任务 | 文件 |
|------|------|
| 新增 `fishing_phase_transition` | `server/src/fishingStateMachine.ts` |
| 新增 `join_pond_success/fail/attempt` | `server/src/index.ts` |
| 新增 `socket_connect/socket_connect_error` 结构化日志 | `server/src/index.ts` |
| 统一 `disconnect/reconnect/leave_pond` payload 字段 | `server/src/index.ts`、`server/src/fishingStateMachine.ts` |
| 扩展 `FishingMetricEvent` 联合类型 | `server/src/fishingMetrics.ts` |
| 新增 player timeline 对 phase transition 的展示 | `server/src/fishingMetrics.ts`、`server/src/admin.ts` |

### 6.2 第二批（P1）

目标：把“钓位 / 咬钩 / pending catch / bot 腾位”补齐，提升业务解释能力。

| 任务 | 文件 |
|------|------|
| spot take/release/fail 埋点 | `server/src/gameState.ts`、`server/src/index.ts` |
| `bite_tick_miss/hit` | `server/src/fishingStateMachine.ts` |
| `pending_catch_created/expired` | `server/src/inventory.ts` |
| `bait_depleted` | `server/src/fishingStateMachine.ts`、`server/src/gear.ts` |
| `bot_evicted_for_human` | `server/src/gameState.ts`、`server/src/bots.ts` |

### 6.3 第三批（P2）

目标：补性能和容量观测，为后续多实例/压测做准备。

| 任务 | 文件 |
|------|------|
| tick 耗时聚合日志 | `server/src/index.ts` |
| snapshot build 耗时 | `server/src/gameState.ts` |
| broadcast fanout | `server/src/index.ts` |
| admin route duration | `server/src/admin.ts` |
| SQLite slow query logging | `server/src/db.ts` 或 DAO 层 |

## 7. 实现约束

### 7.1 命名规范

1. `fishing_metrics.event_type` 使用 **snake_case**
2. 结构化日志前缀保持可 grep：
   - `[socket_connect]`
   - `[join_pond]`
   - `[phase_transition]`
   - `[slow_query]`

### 7.2 入库规范

1. 高价值低频事件才写 SQLite
2. 高频事件优先聚合，不逐条全量入库
3. payload 保持 JSON，可向后兼容新增字段

### 7.3 向后兼容

1. 不破坏现有 Admin summary
2. 旧事件名可保留，新事件作为补充
3. timeline API 若遇老数据无新字段，应正常返回默认值

## 8. 验收标准

### 8.1 P0 验收

| 编号 | 标准 |
|------|------|
| A1 | 单次挂机断线案例可用 timeline 还原 `join -> phase -> disconnect -> reconnect/timeout` |
| A2 | 任意一次 `leave_pond`、`disconnect_timeout`、`join_pond_fail` 均可查到 `playerId/pondId/reason` |
| A3 | `fishing_phase_transition` 能覆盖至少 90% 常见路径：`seated/baiting/casting/waiting/hooked/resolving/disconnected` |

### 8.2 P1 验收

| 编号 | 标准 |
|------|------|
| B1 | 可区分“没鱼”是 `bite_tick_miss`、`bait_depleted`、`disconnect` 还是 `pending_catch_expired` |
| B2 | 可确认钓位释放来源：主动 leave / timeout / 系统 stop |

### 8.3 P2 验收

| 编号 | 标准 |
|------|------|
| C1 | 可统计 95 分位 `tick_fishing_phases_duration_ms` |
| C2 | 可识别慢 Admin 接口和慢 SQL |
