## 1. 背景

Bot 钓获成功走 `handleBotCatch` → **只写背包**，不写 `catch_accept` / `pending_catch_accept`。  
现有看板「日钓获」只数 metrics 成功事件 → 真人可见、bot 产量为 0，与真实生态吞吐严重不符（例：某日真人 metrics 成功 3、bot 背包入库 548）。

**北极星**：看板产量以 **背包入库** 为权威口径，并 **分列真人 / 机器人**（可看总量与分项）。

---

## 2. 口径（已确认）

| 项 | 约定 |
|----|------|
| 产量事件 | `inventory` 表一条入库 = 1 次钓获（`caught_at` 落在统计日） |
| 时区 | **Asia/Shanghai** 自然日（与日报一致） |
| 真人 | `player_id NOT LIKE 'bot-%'` |
| 机器人 | `player_id LIKE 'bot-%'` |
| 总量 | 真人 + 机器人 |

### 展示

| 表面 | 要求 |
|------|------|
| 运营日报 KPI「日钓获」 | 主值 = **总量（背包）**；旁注或副指标：`真人 N · 机器人 M` |
| 运营平台「今日运维」日钓获 | 同上（读 T-1 compact/summary） |
| 增长看板 `daily_catch` | 改为背包总量；增加 `daily_catch_human` / `daily_catch_bot` 序列（折线可叠两条或主线总量+图例分项） |
| `summary.json` | 增加字段（见下）；保留旧 metrics 成功数作对照（可选） |

### `summary.json` / compact（建议）

```json
{
  "kpis": {
    "kpi_daily_catch": { "value": 551, "...": "总量=背包" },
    "kpi_daily_catch_human": { "value": 3 },
    "kpi_daily_catch_bot": { "value": 548 }
  },
  "sections": {
    "catch": {
      "source": "inventory",
      "total": 551,
      "human": 3,
      "bot": 548,
      "metricsAcceptHuman": 3
    }
  }
}
```

`metricsAcceptHuman`（可选）：当日真人 `pending_catch_accept`+`catch_accept`，用于核对背包与确认流是否接近。

### 塘维度

`daily_pond_stats.catch_count` 若继续服务「塘产量」：改为按背包聚合时需能关联塘。  
**MVP**：若 `inventory` 无 `pond_id`，塘表 catch 可暂维持 metrics 或标「仅真人/旧口径」；**优先**在入库链路补 `pond_id`（bot `handleBotCatch` / 真人 accept 写库时带上）后再按塘分列人机。  
本需求 **P0 必须完成**：全站日产量人机分列（不强制同批改塘表）。塘表人机分列标 **P1 同批若易做则做**。

## 3. 非目标

- 不强制 bot 补写 `catch_accept` 埋点（可选后续；本需求以背包为准）  
- 不改游戏内钓鱼数值与 8 小时时长上限  
- 不把 bot 计入 DAU / 留存（仍排除 `bot-%`）
