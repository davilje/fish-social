# 钓点鱼群流动性与分区咬钩

**版本**：v0.4.0  
**状态**：**已实现**
**背景**：当前咬钩 tick 对塘内**全部鱼**逐条计算贡献并求和，钓点权重仅作乘数，不改变「谁能被钓到」。这与「鱼群在钓点间流动、各点位鱼种不同」的产品预期不符。

**关联文档**：[生态调优-咬钩间隔与鱼群恢复](./生态调优-咬钩间隔与鱼群恢复.md)（v0.3.x 补充/咬钩间隔）、[数值重构-品质尺寸咬钩脱钩](./数值重构-品质尺寸咬钩脱钩.md) · [v0.4.0-开发交接](./v0.4.0-开发交接.md)

## 0. 产品决策（已确认）

| # | 问题 | 决策 |
|---|------|------|
| 1 | 迁徙 15min 是否与生态补充同 tick？ | **是** — 在 `tickPondEcology` 同一周期内依次执行：补充 → 迁徙 → 生长 |
| 2 | 是否向玩家展示「本钓点约 N 条鱼」？ | **否** — 正式 UI 不展示；**Debug/Admin 每个钓点仅列出该点 `spot_id` 下的鱼** |
| 3 | 咬钩率下降是否接受？ | **是** — 分区后单点候选变少，**有意降低**咬钩频率；**不做**密度补偿、首版不上调 `QUALITY_BITE_BASE` |
| 4 | Bot 是否只钓本钓点鱼池？ | **是** — Bot 与玩家相同，`rollBiteHook` 仅扫描 Bot 所在 `spot_id` |

## 1. 现状与问题

### 1.1 当前实现（`server/src/fishingSession.ts` → `buildBiteWeights`）

```
对每个钓点 spotId：
  spotMultiplier = getSpotBiteWeight(pondId, spotId)   // 0~5，每 5min 刷新
  for fish in listPondFishEntities(pondId):            // ← 全塘所有鱼
    effectiveBite = spotMultiplier × (baseBite + baitBonus)
  pBite = min(1, Σ effectiveBite)
  若咬钩 → 按 effectiveBite 加权抽一条鱼
```

| 现象 | 问题 |
|------|------|
| 20 个钓点共享同一鱼池 | 换钓点只改变 `spotMultiplier`，**可钓到的鱼集合完全相同** |
| 鱼数越多 Σ 越大 | 大塘极易 `pBite → 1`，咬钩间隔 300s 下仍偏密 |
| `spot_bite_weights` | 名为钓点权重，实为「该点对**所有鱼**的加成系数」 |
| 无鱼的位置概念 | 无法做「这个湾口才出稀有鱼」「那边刚被钓空」 |

### 1.2 产品预期（策划口径）

1. **鱼群具有流动性**：每隔一段时间，鱼「聚集」的钓点发生变化。  
2. **钓点差异化**：玩家在不同钓点，面对的**鱼集合不同**，而非同一批鱼 × 不同系数。  
3. **咬钩判定局部化**：一次 tick **只对当前钓点范围内的鱼**计算是否咬钩，无需遍历全塘。

## 2. 设计目标与非目标

### 2.1 目标

| # | 目标 |
|---|------|
| G1 | 每条鱼在任意时刻归属**唯一钓点**（`spot_id`） |
| G2 | 定时**迁徙/重分配**，使鱼群在钓点间流动 |
| G3 | 咬钩 tick 仅扫描 `spot_id === 玩家钓点` 的鱼（+ 锁鱼排除） |
| G4 | Admin/Debug 可查看「该钓点当前有哪些鱼、tick 概率」 |
| G5 | 与 v0.3.x 品质/尺寸/脱钩公式**兼容**，只改「候选集」 |

### 2.2 非目标（本版不做）

- 不做 2D/3D 鱼游动动画（仍为数据驱动）
- 不做「同一条鱼在两点之间半途」的连续轨迹
- 不改咬钩状态机阶段、脱钩成长、补充机制（可与 v0.3.2 并行开发）
- 不做跨塘鱼流动

## 3. 核心模型：钓点鱼群（Spot School）

### 3.1 概念

```
鱼塘 (pond)
  ├── 钓点 spot-1 … spot-20     （已有，每塘 20 个）
  └── 鱼 fish                   （每条鱼绑定一个 spot_id）

咬钩时：
  候选鱼 = { fish | fish.pond_id = 塘 AND fish.spot_id = 玩家.spot_id AND fish 未锁定 }
```

**直觉**：把塘想象成 20 个「水湾」，鱼整群归属某一个湾；迁徙就是鱼（或鱼群）换湾。

### 3.2 数据字段

| 字段 | 表 | 说明 |
|------|-----|------|
| `spot_id` | `pond_fish` | 非空，FK 逻辑上对应 `PONDS[].spots[].id` |
| `last_migration_at` | `pond_state` | 可选，整塘上次迁徙时间（调试用） |

播种、系统补充、Admin 重置时：**随机或按规则分配 `spot_id`**。

### 3.3 初始分配

```
seed / supplement 创建鱼时：
  spot_id = weightedPick(pond.spots, habitatWeight)
```

`habitatWeight` 复用或替代现有 `spot_bite_weights.weight`（见 §5）。

## 4. 鱼群流动性（迁徙）

### 4.1 设计意图

- 玩家无法通过「死守一个点」永远钓同一批鱼结构。  
- 冷清钓点会逐渐有鱼迁入；热门钓点鱼被钓走后，下一波迁徙会补入新鱼。  
- 与「钓点权重每 5min 刷新」解耦：**鱼的位置**每 **15min** 与生态补充**同 tick** 迁徙（见 §0）。

### 4.2 新常量（`shared/pondEcology.ts` 或 `shared/fishing.ts`）

```typescript
/** 鱼群迁徙检查间隔 — 与 POND_SUPPLEMENT_CHECK_MS 相同，同 tick 触发 */
export const FISH_MIGRATION_CHECK_MS = 15 * 60 * 1000;

/** 每次迁徙事件中，参与换点的鱼占全塘比例（其余留原钓点） */
export const FISH_MIGRATION_FRACTION = 0.40;

/** 迁徙目的地按钓点栖息地权重抽样；权重 0 的钓点仍可接收（保底均匀项） */
export const FISH_MIGRATION_HABITAT_BLEND = 0.7; // 70% 看栖息地，30% 均匀随机
```

### 4.3 迁徙算法（与补充同 tick）

在 `tickPondEcology(pondId)` 内，当补充检查通过时（同一 15min 窗口）：

```
1. trySupplement(...)        // v0.3.x / v0.3.2
2. migrateFishSpots(...)     // 本 spec
3. growAllFish(...)
```

迁徙逻辑：
spots = pond 的 20 个钓点
habitat[w] = getSpotHabitatWeight(pondId, spotId)  // 见 §5，默认 0~5

对塘内每条鱼 f（按 id 稳定排序后遍历）：
  if random() > FISH_MIGRATION_FRACTION:
    continue  // 本周期不迁徙

  destWeight[s] = habitat[s] × FISH_MIGRATION_HABITAT_BLEND
                + (1 - FISH_MIGRATION_HABITAT_BLEND) × 1
  f.spot_id = weightedPick(spots, destWeight)

更新 pond_state.last_migration_at
```

**可选增强（二期）**：

- 同品质鱼小概率「结群」：迁徙时 2~3 条相邻 id 迁往同一点。  
- 被钓空（该点 0 鱼）的钓点，下周期 **`FISH_MIGRATION_FRACTION` 加倍**吸引迁入。

### 4.4 时间线示例（静心湖 80 鱼 / 20 点）

| 时刻 | 事件 |
|------|------|
| T+0 | 初始：每点约 4 条，品质随机 |
| T+15m | **同 tick**：补充 + 40% 鱼（约 32 条）换点 |
| T+30m | 再次迁徙；玩家需关注「哪个点现在鱼多」 |

## 5. 钓点栖息地权重（`spot_bite_weights` 语义升级）

### 5.1 现状

- 表 `spot_bite_weights(pond_id, spot_id, weight)`，`weight ∈ [0, 5]`，每 5min 刷新。  
- 仅用于 `calcFishBiteContribution(spotMultiplier, baseBite, bait)` 的乘数。

### 5.2 新语义（建议列名仍用 `weight`，文档称 **栖息地指数**）

| 用途 | 公式 |
|------|------|
| **迁徙目的地** | 鱼迁入该点的概率 ∝ `weight`（§4.3） |
| **咬钩乘数** | 仅对**本点鱼**仍用 `spotMult × baseBite`（范围不变） |

含义：栖息地好的湾口**鱼更多、且单条更易咬钩**；差湾口鱼少、咬钩也弱——双重差异，鼓励换点。

### 5.3 刷新节律

| 机制 | 间隔 | 说明 |
|------|------|------|
| 栖息地 weight 刷新 | **5 min**（保持） | 影响咬钩乘数 + 下几次迁徙倾向 |
| 鱼 spot 迁徙 | **15 min**（新） | 改变各点鱼数量与结构 |

## 6. 咬钩公式变更（D9）

### 6.1 新流程

```
buildBiteWeights(pondId, spotId, ...):
  if isPondDepleted(pondId): return null

  spotMultiplier = getSpotBiteWeight(pondId, spotId)
  candidates = listPondFishAtSpot(pondId, spotId)   // ← 仅本点
            .filter(f => !excludeIds.has(f.id))

  for fish in candidates:
    effectiveBite = calcFishBiteContribution(spotMultiplier, baseBite, baitBonus)

  totalEffective = Σ effectiveBite
  pBite = calcTickBiteProbability(totalEffective)   // 仍为 min(1, Σ)
  加权抽选 fish
```

**删除**：对 `listPondFishEntities(pondId)` 全量遍历。

### 6.2 数值影响（必读）

| 场景 | 全塘求和（现） | 本点求和（新） |
|------|----------------|----------------|
| 80 鱼 / 20 点，均分 4 条/点 | Σ≈80 条贡献，**极易 pBite=1** | Σ≈4 条，**pBite 显著下降** |
| 1 人在点 A | 与全塘 80 鱼竞争 | 仅与点 A 的 ~4 条竞争 |

**结论**：分区后单点咬钩率会大幅下降，这是**已确认的产品目标**（换点、等迁徙、追鱼群）。

**数值策略（已定）**：

- 采用 **方案 A：接受降频** — 不改 `calcTickBiteProbability`，**不做**局部密度补偿，**首版不调** `QUALITY_BITE_BASE`。
- 上线后用 `simulate-pond-day.ts` 记录分区后 24h 渔获，仅作观测，非阻断调参条件。

### 6.3 同点多人

同一 `spot_id` 上多名玩家：**共享同一候选鱼池**（与现网共享全塘池类似，但池子更小）。  
锁鱼机制不变：已 hook 的鱼从池中排除。

### 6.4 塘内总鱼数 = 0

仍 `isPondDepleted`；补充/兜底后新鱼带 `spot_id`，无需全塘遍历。

## 7. 服务端改动摘要

| 模块 | 改动 |
|------|------|
| `pond_fish` | 新增 `spot_id TEXT NOT NULL`；索引 `(pond_id, spot_id)` |
| `pondEcology.ts` | `migrateFishSpots(pondId)`；**与 `trySupplement` 同 tick**；`insertPondFish` 写 `spot_id` |
| `fishingSession.ts` | `buildBiteWeights` → `listPondFishAtSpot` |
| `fishingDebug.ts` | **每钓点 tab/区块仅展示该 `spot_id` 的鱼**及咬钩贡献；**不**在全塘列表重复算入他点鱼 |
| `bots.ts` | Bot `rollBiteHook` 与玩家一致，**仅本钓点候选** |
| `simulate-pond-day.ts` | 鱼带 `spot_id`；咬钩只扫本点；可选迁徙步进 |

**查询示例**：

```sql
SELECT * FROM pond_fish WHERE pond_id = ? AND spot_id = ?;
```
