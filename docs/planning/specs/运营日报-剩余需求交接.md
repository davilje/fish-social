## 3. 需求详规

### 3.1 D-L3-05 — 鱼塘生态健康日报

**目标**：日报 §6 能回答「各塘会不会枯竭 / 品质结构是否崩」。

#### 建设要点

1. 新增日末快照步骤（可独立脚本后由 pipeline 调用）：
   - 建议路径：`scripts/analytics/ecology-daily-snapshot.mjs`
   - 产出：`docs/analytics/daily/<date>/ecology-snapshot.json`
   - 内容：每塘 `pondId` · `population` · `maxPopulation` · `popRatio` · 分品质 count · `avgSizeM`
2. 数据源：运行时 `pond_fish` / ecology 表（与 Admin 鱼群同源）；统计时刻 = 日批运行时「日末近似」（00:30 跑 T-1 时，用 T-1 结束前最后一次可用状态；若仅有当前内存态，文档注明局限并优先落库快照）。
3. **更稳方案（推荐）**：日批前或 23:55 写入 `daily_pond_ecology` 表（`date_key, pond_id, population, max_population, quality_json, avg_size_m`），日报只读表。
4. `compute-daily-summary.mjs` 的 `sections.ecology` 填真实数据；去掉「仅有 avg」占位。
5. `generate-daily-ops-report.mjs` §6：分塘表 + 人口率；**任一塘 `popRatio < 70%` → 状态红**，并写入 `alerts`（已有 `alert_pop_low` 需基于快照人口率，而非仅 metrics 均值）。

#### 验收

| # | 标准 |
|---|------|
| 1 | `ecology-snapshot.json` 或 `daily_pond_ecology` 含四塘数据 |
| 2 | `report.html` §6 可见人口/上限/人口率/品质占比 |
| 3 | 人为造「某塘 popRatio=60%」→ 告警清单出现 `alert_pop_low` |
| 4 | `npm run verify:daily-ops-report` 扩展覆盖生态字段；或新增 `verify:daily-ops-r1` |

### 3.2 D-L3-04 — 经济 faucet / sink 日报

**目标**：日报 §5 能回答「金币进了多少、出了多少、净变化是否连续失衡」。

#### 建设要点

1. **埋点（阻塞项）**  
   - 卖鱼/收金币等 faucet 路径必须写 `fishing_metrics`（或专用 economy 事件）：  
     建议 `event_type`: `gold_earn` / `fish_sell`（二选一，文档与 schema 统一）  
     `payload`: `{ amount, source, fishId?, quality? }`  
   - 现有 sink：`bait_buy` / `tackle_buy` / `tackle_repair` 的 `cost` 已部分可用，核对 payload 字段一致。
2. `compute-daily-summary.mjs`：
   - `economy.faucetTotal` · `economy.sinkTotal` · `economy.net = faucet - sink`
   - 分项：按 `source` / baitId / tackleId
   - **连续 3 日 `|net|` 超阈值或 faucet≪sink**：写入 alert，如 `alert_economy_imbalance`
3. `report.html` §5：faucet / sink / 净变化卡片 + 结构表；无 faucet 埋点时不得显示假 0，应失败或明确「数据缺失」阻断验收。

#### 验收

| # | 标准 |
|---|------|
| 1 | 测试库写入卖鱼事件后，日报 faucet &gt; 0 |
| 2 | 页面可见 faucet、sink、净变化 |
| 3 | 模拟连续 3 日净流出超阈值 → `alert_economy_imbalance` |
| 4 | 无埋点环境：CI 用 fixture 覆盖；生产缺埋点不得静默通过 |

---

### 3.3 D-L3-03 — 留存与会话时长分析

**目标**：能回答「人回不回来、玩多久」。

#### 建设要点

1. **留存**  
   - Cohort：以「当日新增玩家」为分母（`players.created_at` 落在 date_key）  
   - D1：次日有任意 metrics 的唯一玩家占比  
   - D7：第 7 日回访占比  
   - 产出：`sections.retention = { cohortSize, d1Rate, d7Rate }`（D7 需历史日补跑或延迟到 T+7 再算；报告可展示「尚未到期」）
2. **会话时长**  
   - 用 `daily_player_stats.fishing_ms`：人均、P50/P90（若仅有日合计则先人均 + 分布粗桶）  
   - 可选：`fishing_start` 次数 / 钓鱼 DAU = 人均 session 数
3. `report.html` 增加 §2 扩展或独立「留存」小节；上周 cohort 可用 `weekly` 附页或同页近 7 日表。

#### 验收

| # | 标准 |
|---|------|
| 1 | summary 含 `retention` 与 session 时长字段 |
| 2 | 用 fixture 可算出 D1（人为两日登录） |
| 3 | 报告页可见留存/时长；无数据时注明原因 |

### 3.4 D-L3-07 — 规则版本切分分析

**目标**：调参前后可对比，顶栏不再写死 `rulesVersion: 'live'`。

#### 建设要点

1. 日批写入真实规则版本：来源优先级  
   - `game_config` / 运行时 config 的 `rulesVersion` 或 `configVersion`  
   - 环境变量 `RULES_VERSION`  
   - 兜底：`package.json` version + 日期  
2. `summary.meta.rulesVersion`、`compact.rulesVersion`、`report.html` 顶栏展示。  
3. 对照增强：`live-vs-sim` 或日报 §7 支持按 `rulesVersion` 分组看近 7 日 `kpi_daily_catch`（简单表即可）。

#### 验收

| # | 标准 |
|---|------|
| 1 | 改 env/配置后重跑日报，顶栏版本变化 |
| 2 | 近 7 日表可看到不同 `rulesVersion` 行（若仅一天则一行） |
| 3 | 禁止硬编码写死 `'live'` 作为唯一来源 |

---

### 3.5 D-L3-08 — 运营指标告警（Webhook）

**目标**：超阈值时主动通知策划，不必每天打开 HTML。

#### 建设要点

1. 日批末尾：若 `summary.alerts` 存在 `level === 'bad'`（或配置的 warn），POST `ALERT_WEBHOOK_URL`（与现有告警通道复用若已有）。  
2. Payload 建议：`{ dateKey, alerts[], reportPath, rulesVersion }`  
3. 环境变量：`DAILY_ALERT_WEBHOOK_URL`（可回落到 `ALERT_WEBHOOK_URL`）；`DAILY_ALERT_MIN_LEVEL=bad|warn`  
4. 失败不阻断日报文件生成（log warn）；提供 dry-run：`DAILY_ALERT_DRY_RUN=1`  
5. 文档更新：`docs/ops/daily-analytics-cron.md` 增加 Webhook 说明。

#### 验收

| # | 标准 |
|---|------|
| 1 | dry-run 下打印将发送的 payload |
| 2 | mock HTTP 收到含 `alert_*` 的 body |
| 3 | 无 Webhook 配置时跳过且 exit 0 |
| 4 | 与 `verify:daily-ops-report` 或新 `verify:data-platform-dp-c2` 覆盖 |
