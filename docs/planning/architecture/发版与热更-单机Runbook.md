# 发版与热更 — 单机 Runbook（OPS-RELEASE-1）

| 项 | 内容 |
|----|------|
| 关联规格 | [发版与热更策略.md](../specs/发版与热更策略.md)（**OPS-RELEASE-1**） |
| 适用拓扑 | **单机** Node + SQLite（`data/fish-social.db`） |
| 非目标 | 客户端 OTA（Expo Updates / CodePush）· 多机滚动（BE-OPT-E） |

本文给运营 / 后端维护执行用。策略分类以 OPS-RELEASE-1 spec §2–§3 为准；此处展开可勾选步骤。

---

## 1. 三类更新（速查）

| 类型 | 含义 | 单机是否停服 |
|------|------|----------------|
| **A. 配置热更** | `game_config` 等 KV，不换进程包 | **不停服** |
| **B. 服务端发版** | 换 Node 代码 / DB 迁移 | **短停服（分钟级）** |
| **C. 客户端 OTA** | 不经商店更新 JS/资源 | **本阶段不做**；另立 `OPS-RELEASE-OTA` |

决策矩阵见 spec §3。务实目标：A 真正不停服；B 接受短窗；不承诺多机零停机。

---

## 2. A 类：配置热更（不停服）

前置：FEAT-05 C1 / Admin 双人批准已可用。

1. 运营在 Admin「参数 / 配置」提交变更（写清变更原因）。
2. 第二人 **批准**（勿自批自批绕过）。
3. 确认运行时已 `refresh`：A2 / 生效值面板与预期一致；观察关键日志无配置解析错误。
4. 异常 → **配置回滚**到上一已批准版本（Admin 回滚入口）；再核对生效值。
5. 不重启进程；不碰 SQLite 备份（除非配置写库失败需排障）。

回滚入口：Admin 配置历史 / 上一版 `game_config`；勿用「重装镜像」当配置回滚首选。

---

## 3. B 类：服务端发版（短停服）

### 3.1 发版前

- [ ] 确认变更属 B（代码/迁移），非可走 A 的纯数值
- [ ] 破坏性协议 / DTO：已升 `protocolVersion` 并通知客户端纪律（UNITY-P0）
- [ ] 准备回滚点：当前镜像 tag / git SHA / 备份文件名

### 3.2 停服窗口

1. **公告 / 踢人**（若有运维入口）：尽量让在钓玩家收杆离塘。
2. **停服**：停止 Node / `docker compose down`（按实际部署）。
3. **SQLite 备份**（必做）：
   ```bash
   # 示例：停写后拷贝（路径以环境为准）
   mkdir -p backups
   copy data\fish-social.db backups\fish-social-%DATE%.db
   # 或项目已有备份脚本（若配置了 npm run / scripts 备份）
   ```
   保留至少最近 7 份；破坏性迁移前再多留一份带标注的备份。
4. **部署代码**：拉包 / 换镜像 / `npm ci` + `npm run build:shared`（按环境）。
5. **迁移**：启动时由服务自动跑迁移；观察启动日志 `Database ready` / migration 行无失败。
6. **冒烟**：
   ```bash
   npm run verify:server-boot
   ```
   或等价：进程起来后 `GET /health` → 200。
7. **健康检查**：
   - `GET http://<host>:3001/health` → 200
   - （可选）`/ready` 若启用
   - 抽查关键日志：无持续 error；Socket 可连
8. **开门**：恢复对外流量 / 取消维护公告。

### 3.3 发版后观察（15–30 分钟）

- `/health` 持续 200  
- 进塘 / 开钓 / 收杆各一次（人工或脚本）  
- 日批若临近：确认 `daily-pipeline` 仍可跑（不阻塞开门）

## 4. 回滚流程

| 场景 | 动作 |
|------|------|
| A 配置错误 | Admin 回滚上一批准版 → 核对生效值 |
| B 新包异常（迁移未破坏数据） | 停服 → 换回上一镜像/SHA → 启动 → `/health` → 开门 |
| B 迁移已写坏数据 | 停服 → **恢复发版前 SQLite 备份** → 换回旧包 → `/health` → 开门；再开缺陷单 |
| 不确定 | 优先恢复服务可用；再查日志；勿在未备份时二次迁移 |

---

## 5. 停服边界（写清预期）

| 可尽量不停 / 极短窗 | 必须停服 |
|---------------------|----------|
| A 配置热更 | SQLite 破坏性迁移、清库、不可逆数据手术 |
| 兼容性小改（旧客户端仍可用）的热替换尝试 | 破坏性 API/Socket / 必改事件名 |
| — | 单机换包无法双进程热切时的常规发版 |

单机 **不承诺**「绝对不停机」；目标是分钟级短窗 + 可回滚。

---

## 6. OTA（C 类）— 暂不实现

- 本阶段 **不**接入 Expo Updates / CodePush / 商店热更 CDN。  
- 触发另立项目的条件：正式客户端形态确定，且接近商店打包。  
- 另立项建议名：`OPS-RELEASE-OTA`（以当时策划编号为准）。  
- 多机滚动发布归 **BE-OPT-E**，不在本 Runbook。
